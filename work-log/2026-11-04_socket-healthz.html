Added GET /healthz to KuboCare-Socket so the Uptime Kuma Socket monitors (UAT, PROD-IN, PROD-US) get a 200 instead of a 404, matching the gateway's FastAPI endpoint.

Back to top

Why

  • Uptime Kuma (uptime.kubocare.ai, from the kubocare-observability repo) marks a monitor Up only on HTTP 200.
  • The gateway has /healthz. The socket server had no route that returned 200, so all three Socket monitors showed 0% even though the service was running.
  • Requested by the observability owner on 2026-11-03.

What changed

KuboCare-Socket dev-in-hrishikesh (merged dev-in cae0cb4 first)5e5fb00lib/healthz.js, lib/healthz.test.mjs, index.js, config.js
  • GET /healthz returns 200 {"status":"ok","env":NODE_ENV} with Cache-Control: no-store. Same body shape as the gateway.
  • Shallow on purpose: it answers "the process is up". It does not check MQTT, Redis or Postgres, so a broker blip does not mark the socket down.
  • Feature flag: none. Small, read-only, zero-risk, under the updated gating rule (no flag for zero-risk additions).

Back to top

Ship gate

  • Efficient and secure: one in-memory route, no I/O. No auth needed: it returns only "ok" and the env name, the same as the gateway. No tokens or resident data.
  • Regressions: the route is registered after helmet and before socket.io attaches; socket.io only handles /socket.io/, so the paths do not overlap. Checked: the handshake still returns 200 and bare / is still 404.
  • Tests: new node lib/healthz.test.mjs (GET 200 with the body and no-store, HEAD 200, POST 404, other paths 404). Existing socketAuth, ghostFilter and vizRaw tests still pass. Manual: started the real server on a spare port with Redis down: /healthz returned 200, which proves the check is shallow.
  • Not verifiable from here: whether each environment's nginx forwards /healthz to Node, or only /socket.io/. Check once promoted.

What is left

  • After deploy, curl -i https://<socket host>/healthz per env. A 404 then means nginx needs a location for /healthz.
