Prod-US ran out of CPU when boards were added. Fixed three ingest costs in the gateway relay: the Redis frame ring drops from about 20 minutes to about 5, non-leader workers stop parsing radar frames, and the frame assembler no longer rescans everything on every message.

Back to top

Why

  • On 2026-11-18, adding more boards on prod-us exhausted the gateway CPU, seen as slow Redis writes.
  • Every radar frame (v6 + v7 + v8 joined) goes to a per-board Redis stream stream:raw:<board>. The cap was 24,000 frames, about 20 minutes at the radar's 20 fps. Replay only reads the fall window until the auto-clip cuts it; older replays already come from S3 and the saved clips.
  • Tracing the ingest path found two costs that grow with board count:
    • Gunicorn runs one worker per core, and every worker parsed every radar message. Only the elected ingest leader uses them.
    • The frame assembler scanned every pending frame and rebuilt its whole dedupe map on every v6 / v7 / v8 message. That work grows with the square of the board count.

What changed

ChangeFiles

Startup warning if the ring is shorter than the fall clip needs (required_ring_sec()).relay/config.py, relay/relay_app.py

Feature flag: none. The ring size is a constant, the env cleanup removes dead code, and the two CPU fixes keep behaviour the same. Existing streams shrink on their own on the next write; no migration.

Server env files

The vault copies of the env files (DEV, UAT, PROD-IN, PROD-US) all set STREAM_MAXLEN=24000, so the servers held about 20 minutes per board. UAT, PROD-IN and PROD-US also set RELAY_HOST and RELAY_PORT. The relay now ignores all of these lines, so leaving them does no harm. Delete them on each server during the next env edit.

All four also set INCIDENT_WINDOW_SEC=30. The ring then needs about 63 s, which 5 minutes covers.

Test results

  • pytest app/test: 125 passed (114 before plus 11 new), no failures, with and without .env sourced.
  • The new throttle test fails on the old assembler, so it guards the fix.
  • Assembler CPU per second of radar data, measured by replaying synthetic frames at 20 fps:

Above 1,000 ms the single event loop can't keep up, and frames queue behind it. That likely explains the prod-us slowdown more than Redis itself.

Ship gate

Efficient and secure

  • Assembler work per message is now constant instead of growing with board count. Non-leaders skip the parse entirely. Redis memory per board drops by 75%.
  • No new endpoints, inputs or secrets. Leftover env lines are ignored (extra="ignore").
  • Not done: non-leaders still receive radar frames over MQTT, and the S3 sink still creates a client per minute rollup.

Regressions to watch

  • A replay older than 5 minutes now comes from S3 raw (20 min) or the clip instead of Redis. It will be slightly slower, but the data is the same.
  • The auto-clip restart backfill only rescues falls still in the ring, so its window shrinks to 5 minutes. The S3 and local clip paths are unchanged.
  • A frame missing one sub-topic now flushes after up to 1.2 s instead of 1.0 s.
  • Before the first leader election, non-leaders already dropped radar frames, so that behaviour is unchanged.

Tests

  • Automated, new: partial frame flush after timeout, sweep throttle, complete frame inside the throttle gap, straggler dedupe and bounded memory, non-leader skips the parse, malformed frame dropped silently, falls and alerts still handled on non-leaders, leader and ungated paths unchanged, ring covers the clip in both post-window modes, leftover env vars ignored.
