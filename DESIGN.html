  • gateway owns the Postgres schema (Alembic), REST API, alerts and notifications.

  • Frontend calls both. Locale (in, jp, us) picks the API and socket subdomain.
  • fds-inference scores raw radar falls and forwards only confirmed ones.

Fall alert path

  1. Radar publishes a raw fall (type: FDS). Kafka Connect copies it to Kafka topic fds.
  2. fds-inference scores it with an XGBoost model on 5 s of obj data either side. Every score is archived to Postgres table fds_inference_results.
  3. Confirmed falls are republished byte for byte to MQTT alerts with type: kubocare_model. No confidence value is in the payload.
  4. gateway (app/services/mqtt_callbacks.py) handles it. With FALL_ALERT_SOURCE=model (default) raw FDS falls do not alert. Incidents are matched by exact string on location, time, fds_fn.
  5. gateway sends SMS, WhatsApp, push, Slack. Socket re-emits fall_data to the global room from Redis alert cards.
  6. Resolving from Slack makes the gateway publish alerts/refresh; socket re-scans and re-emits.

Delivery is at least once. Dedupe on board_sn + fn + time.

Auth

  • Users log in via the gateway (fastapi-jwt-auth). Frontend keeps token, refreshToken, roleId in cookies and refreshes once on 401/422.
  • Socket verifies the same JWT with the shared secret and checks board access through the resident and user hierarchy tables. Role 1 bypasses.
  • External tenants get their own JWT from /api/v1/tenant/auth/token, connect on the socket's /tenant namespace and receive filtered fields. Socket asks the gateway for tenant config over an internal API key.
  • Roles: 1 Kubocare Admin, 2 Community Owner, 3 Community Manager, 4 Family Member, 5 Call Centre, 6 Caregiver, 7 Resident.

Feature gating

  • gateway: *_ENABLED env flags in app/core/config.py, default off, checked in the service.
  • socket: envBool flags in config.js; when off, data passes through untouched.
  • frontend: no system yet. Use EXPO_PUBLIC_<FEATURE>_ENABLED, default off. UI gating is not security; the gateway enforces too.
