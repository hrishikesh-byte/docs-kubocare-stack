All docs

How the KuboCare monitoring stack (our in-house Datadog replacement) collects logs and metrics from every VM, stores them, shows them in Grafana and raises alerts, explained in plain words with diagrams, the code path and the gaps I found.

One sentence version. A small agent (Grafana Alloy) on every server pushes that server's logs and numbers over HTTPS to a central monitoring VM per region, which stores them cheaply in Azure Blob for 90 days and lets engineers search, graph and get alerted from one Grafana at monitoring.kubocare.ai.

Repo: kubocare/kubocare-observability (org repo, branch main, read at b0927fa, 2026-11-03). It is pure config: Docker Compose, YAML and Alloy files, plus three small scripts. No application code.

The big picture

Three kinds of traffic hit the monitoring VM: agents pushing data, browsers sending front-end telemetry, and humans opening Grafana. Nginx sorts them by domain name.

DomainWho uses itWhat nginx does
monitoring.kubocare.ai (OBS_DOMAIN)HumansProxies to Grafana. Also accepts /faro/.
obs-in.kubocare.ai (INGEST_DOMAIN)Agents, browsers, peer reads/loki/api/v1/push to Loki, /api/v1/write to Mimir, /faro/ to Alloy, read paths /loki/ and /prometheus/ only from PEER_ALLOW_IP. Anything else redirects to the portal.
uptime.kubocare.ai (UPTIME_DOMAIN)HumansProxies to Uptime Kuma (status checks, status pages).
obs-us.kubocare.aiUS agents, India GrafanaSame ingest rules as obs-in, on the US VM. Only India's public IP may read.

Words you need

TermPlain meaning
MetricA number over time, like CPU % or "rows pending". Cheap to store, good for graphs and alerts.
Log lineOne line of text a container printed. Good for "what exactly happened".
LabelA tag on every metric and log, like env=prod, host=vm-kubo-prod-db-001, role=db. This is how you filter.
Grafana AlloyThe agent. Reads logs, collects metrics, attaches labels, pushes them out.
MimirLong-term metric database. Speaks the Prometheus query language (PromQL).
LokiLog database. Indexes labels only, not the text, so it is cheap. Queried with LogQL.
PrometheusHere only a small local scraper that checks the stack itself and forwards to Mimir.
Remote writeThe HTTP protocol Alloy uses to push metrics into Mimir.
FaroGrafana's browser SDK: JS errors, page speed, user sessions (RUM, real user monitoring).
Grafana orgA separate workspace inside one Grafana. Org 1 = India, org 2 = US.
Compose profileA tag on a service so it only starts when asked, for example --profile ui for Grafana.

Code flow: life of one log line

Say the gateway container prints ERROR Context or Resident not found on vm-kubo-prod-app-001.

  1. Discover. discovery.docker lists running containers via the Docker socket; discovery.relabel turns Docker metadata into labels container, service, project. (base.alloy)
  2. Read. loki.source.docker tails that container's stdout.
  3. Clean. loki.process "parse" drops Kafka Connect's INFO WorkerSourceTask noise (about a quarter of all volume), finds the first severity word with a regex, normalises WARNING to WARN and sets it as the level label.
  4. Tag and push. loki.write "obs" adds env, host, role and POSTs to $OBS_URL/loki/api/v1/push with basic auth.
  5. Front door. nginx on obs-in checks the password against nginx/htpasswd and proxies to loki:3100.
  6. Store. Loki indexes the labels, compresses the text into chunks in Blob container loki-chunks. The compactor deletes chunks older than LOKI_RETENTION_PROD (90 days; uat has its own LOKI_RETENTION_UAT).
  7. Find it. In Grafana Explore pick Loki and run {env="prod", service="gateway", level="ERROR"}, or use the Log lines panel on the KuboCare Overview dashboard.

Code flow: life of one metric

Example: the "fall incidents in tenant scope" number from the prod DB.

  1. Query. Every 60 s the db-role prometheus.exporter.postgres runs the SQL in postgres-queries.yaml as alloy_monitor. It returns kubocare_fall_incidents_in_tenant_scope_24h and friends.
  2. Scrape. prometheus.scrape "postgres" collects it and hands it to prometheus.remote_write "obs", which adds env, host, role.
  3. Push. POST to $OBS_URL/api/v1/write. nginx checks basic auth and rewrites to Mimir's /api/v1/push.
  4. Store. Mimir keeps the last few hours on local disk, cuts 2-hour blocks and uploads them to mimir-blocks. Its compactor deletes blocks older than MIMIR_RETENTION (90d).
  5. Use. The Overview dashboard stat panel and the kc-fall-webhooks-stopped alert both query it through the datasource named Mimir (uid prometheus).

Product health from Postgres (the clever bit)

Host metrics tell you a server is alive. They do not tell you the product is working. Some KuboCare failures never throw an error: a table just stops changing. postgres-queries.yaml reads the KuboCare schema directly so those become alertable numbers.

MetricWhat it countsAlert built on it
kubocare_fall_incidents_in_tenant_scope_24hFall or suspected incidents in 24 h on devices listed in an active tenant's integration_config.devicesFall webhooks stopped reaching tenants: incidents > 0 but webhooks = 0 for 30 min (critical)
kubocare_fall_webhooks_24hFall webhook rows created in webhook_outbox in 24 h
kubocare_fall_outbox_pending, _outbox_failed_24hWebhooks waiting, webhooks failedOutbox not draining: pending > 20 or failed > 5 (warning)
kubocare_fall_model_confirmations_24hfall_observations rows of type kubocare_model (fds-inference confirmations)Dashboard only
kubocare_freshness_age_seconds{source}Age of the newest row in insight_baselines and each daily wellness_* typeBaselines older than 26 h; wellness older than 40 h (Databricks notebook missed a run)

One Grafana, two regions

Grafana runs only in India. The US VM is "headless": it stores data but has no UI. Two tricks make this work.

  • Same datasource ids in both orgs. Org 1 India's Mimir and Loki point at local containers; org 2 US's point at $PEER_OBS_URL with basic auth. Both use uids prometheus and loki, so one dashboard JSON and one rule file work in both orgs unchanged. Switch region with the org switcher, top left.
  • US read path is locked down. The US nginx only serves /loki/ and /prometheus/ to PEER_ALLOW_IP (India's public IP) and still asks for the password.

Org 2 cannot exist before Grafana boots, but provisioning that mentions org 2 kills Grafana at boot. bootstrap-orgs.sh breaks the loop: it boots Grafana once with an empty provisioning folder, creates org 2 through the API, then restarts it with full provisioning.

Security model

  • TLS everywhere public. One Let's Encrypt cert per VM covering all its domains, HSTS on, TLS 1.2+.
  • Write path: basic auth, one shared user alloy in nginx/htpasswd for all hosts.
  • Read path for the peer: IP allowlist plus the same basic auth.
  • Humans: Google SSO limited to kubocare.com, everyone lands as Viewer, sign-up and anonymous off. Local admin is break-glass only.
  • Cloud: managed identity, no storage keys or client secrets in files.
  • Patient data: logs can contain PHI, which is why US logs stay in US Blob and retention is capped.
  • Agents: the host Alloy is privileged with root filesystem read access. Needed to see everything, but it makes the agent host-level sensitive.

Setup in short

Central VM (India)

cp .env.example .env                                   # fill domains, Azure, passwords, SMTP
htpasswd -bc ./nginx/htpasswd alloy "<push password>"
docker compose run --rm -p 80:80 -e CERTBOT_STANDALONE=1 certbot
docker compose up -d loki mimir prometheus alloy nginx
./scripts/bootstrap-orgs.sh                            # starts Grafana, creates orgs
docker compose --profile ui up -d uptime-kuma
docker compose --profile ui --profile setup run --rm uptime-kuma-init

The US VM is the same without the ui profile, with OBS_ENV_LABEL=us, PEER_ALLOW_IP set to India's IP and UPTIME_DOMAIN empty.

Each monitored VM

cd /opt/kubocare-observability/hosts
./install.sh <uat|prod> <app|db|kafka|mqtt|vpn> <hostname> https://obs-in.kubocare.ai   # obs-us for US
docker logs alloy --tail 25
curl -I https://obs-in.kubocare.ai/api/v1/write        # 401 means TLS and nginx are reachable

Then in Grafana Explore: up on Mimir should list the host, {env="uat"} on Loki should stream logs.

Gaps and gotchas I found

From reading the config only. Nothing here was tested against the live VMs, so treat each as "likely, verify first".

SevFindingEvidenceEffect
HighThree alerts fire when things are healthykc-baselines-stale, kc-wellness-stale and kafka-connect-mqtt-source already filter inside the query (> 93600, == 0), so a healthy system returns no data, and they set noDataState: Alerting.Constant false alerts in the ops inbox, so real ones get ignored. Fix: query the raw value and let threshold C decide, or set no-data to OK.
HighPostgres KPI SQL probably never loadsdb.alloy reads /etc/alloy/postgres-queries.yaml; hosts/docker-compose.yml mounts it at /etc/alloy-config/postgres-queries.yaml.No kubocare_* metrics. The fall-webhook and outbox alerts use no-data OK, so they stay silent exactly when they matter.
MedDead man's switch is not wiredDEADMAN_PING_URL is passed to Grafana but no contact point uses it. The heartbeat routes to the default email receiver.If the whole stack dies, nobody is told; meanwhile ops gets a heartbeat email every 4 h.
MedDaily pipeline alert is a placeholderRule comment says to adjust the regex; no daily-pipeline service is known, and no-data is Alerting.Fires forever until wired to a real log line.
MedBrowser RUM is not liveThe web app still ships Datadog (KuboCare-frontend-WEB/observability/datadog.web.ts), no Faro SDK. nginx answers CORS preflight with a bare 204, likely without CORS headers.Faro path is ready on the server side only. Test a real cross-origin POST before switching.
LowSome scrape targets are always downGateway has no Prometheus /metrics endpoint; Kafka JMX on 9404 is not added yet; empty FDS_REDIS_ADDR points at port 1; obs-us Prometheus scrapes a Grafana that is not there.Noise in up, no alert fires on it. The gateway needs instrumenting before app metrics exist.
LowDocs drift.env.example and hosts/.env.example say obs-india.kubocare.ai; README and nginx default say monitoring / obs-in. prometheus.yml calls itself a remote-write receiver but it only scrapes the stack. Loki comment says uat keeps less, but both are 90 days.Confusing on a fresh install.
LowOne shared push passwordEvery host and the peer use user alloy. The committed README also contains real-looking cloud identifiers and example passwords.One leak lets anyone push junk data into any region. Rotation means touching every VM.
LowSingle node, no replicationMimir and Loki use replication factor 1 and in-memory rings.Fine for cost. Losing the VM disk loses the last couple of hours not yet in Blob.
